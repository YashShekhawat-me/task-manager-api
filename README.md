# Task Manager API

A secure task management API built with Node.js, Express, PostgreSQL, and JWT authentication. It supports user registration/login and task management with filtering, sorting, and pagination.

## Overview

This project exposes a REST API for managing tasks per authenticated user. Each task belongs to a user and is protected behind JWT-based authorization. The API uses a layered architecture with routes, controllers, services, repositories, and middleware for validation and error handling.

## Features

- User registration and login
- JWT authentication for protected routes
- Create, read, update, and delete tasks
- Task filtering by completion status
- Search by task title
- Sorting by `id` or `title`
- Pagination with `limit` and `offset`
- Request validation and centralized error handling
- PostgreSQL persistence with the `pg` client
- Response timing logs in non-test environments

## Environment Configuration

Create a `.env` file in the project root with your database and JWT settings:

```env
DB_USER=postgres
DB_HOST=localhost
DB_NAME=taskmanager
DB_PASSWORD=your_password
DB_PORT=5432
JWT_SECRET=your_super_secret_key
```

For tests, create a `.env.test` file as well:

```env
DB_USER=postgres
DB_HOST=localhost
DB_NAME=task_manager_test
DB_PASSWORD=your_password
DB_PORT=5432
JWT_SECRET=your_super_secret_key
```

Note: the app reads `.env` or `.env.test` based on `NODE_ENV` when establishing the DB connection.

## Database Setup

Create the required PostgreSQL tables:

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tasks (
  id SERIAL PRIMARY KEY,
  title VARCHAR(100) NOT NULL,
  completed BOOLEAN NOT NULL DEFAULT FALSE,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

## Authentication

The API uses JWT authentication. Register or login first, then send the returned token in the `Authorization` header:

```http
Authorization: Bearer <your_token>
```

### POST /auth/register

Creates a new user and returns the created user.

Request body:

```json
{
  "email": "user@example.com",
  "password": "MyPassword123"
}
```

Example:

```bash
curl -X POST http://localhost:3000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"MyPassword123"}'
```

### POST /auth/login

Logs in an existing user and returns a JWT token.

Example:

```bash
curl -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user@example.com","password":"MyPassword123"}'
```

Successful response example:

```json
{
  "successful": true,
  "message": "authentication successful",
  "token": "<jwt_token>",
  "user": {
    "email": "user@example.com",
    "id": 1,
    "created_at": "2026-10-22T12:00:00.000Z"
  }
}
```

### GET /auth/me

Returns the current authenticated user's ID.

```bash
curl http://localhost:3000/auth/me \
  -H "Authorization: Bearer <your_token>"
```

## Task Endpoints

All `/tasks` routes require a valid JWT token.

### GET /

Returns a welcome message.

```bash
curl http://localhost:3000/
```

### GET /tasks

Fetches tasks for the authenticated user with optional filtering and pagination.

Query parameters:

- `completed=true|false` — filter tasks by completion state
- `search=some text` — case-insensitive partial title search
- `sort=id|title` — sort field
- `order=asc|desc` — sort direction
- `limit=1..100` — max tasks returned
- `offset=0..n` — items to skip

Example:

```bash
curl "http://localhost:3000/tasks?completed=false&search=read&sort=title&order=desc&limit=10&offset=0" \
  -H "Authorization: Bearer <your_token>"
```

Example response:

```json
{
  "user_id": 1,
  "data": [
    {
      "id": 3,
      "title": "Read the project brief",
      "completed": false,
      "user_id": 1
    }
  ],
  "pagination": {
    "limit": 10,
    "offset": 0,
    "total": 1
  }
}
```

### GET /tasks/:id

Gets one task by ID for the current user.

```bash
curl http://localhost:3000/tasks/1 \
  -H "Authorization: Bearer <your_token>"
```

### POST /tasks

Creates a new task for the authenticated user.

Request body:

```json
{
  "title": "Write the README"
}
```

Example:

```bash
curl -X POST http://localhost:3000/tasks \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <your_token>" \
  -d '{"title":"Write the README"}'
```

### PATCH /tasks/:id

Updates a task title and/or completed status.

Request body:

```json
{
  "title": "Updated task title",
  "completed": true
}
```

Example:

```bash
curl -X PATCH http://localhost:3000/tasks/1 \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <your_token>" \
  -d '{"title":"Updated task title","completed":true}'
```

### DELETE /tasks/:id

Deletes a task by ID for the current user.

```bash
curl -X DELETE http://localhost:3000/tasks/1 \
  -H "Authorization: Bearer <your_token>"
```

## Validation

The API validates:

- email format and password length for auth requests
- task title must be a non-empty string between 1 and 100 characters
- `completed` must be a boolean when provided
- task IDs must be positive integers
- `sort` must be `id` or `title`
- `order` must be `asc` or `desc`
- `limit` must be an integer between 1 and 100
- `offset` must be an integer greater than or equal to 0
- `search` cannot be empty
- request bodies must be JSON objects for task creation and update routes

## Error Handling

The app uses a custom `AppError` class and centralized error middleware. Common responses follow this pattern:

```json
{
  "message": "Task not found",
  "successfull": false
}
```

Examples of common HTTP errors:

- `400` invalid request data or malformed JSON
- `401` missing or invalid token / invalid credentials
- `404` task not found or route not defined
- `409` duplicate email during registration
- `500` unexpected server error

## Notes

- Task access is scoped by `user_id`, so each user sees only their own tasks.
- Response time logging is enabled outside the test environment.
- The project follows a simple layered architecture: routes -> controllers -> services -> repositories -> PostgreSQL.
- This API is intended for local development and can be extended with Docker, database migrations, or a frontend client.
